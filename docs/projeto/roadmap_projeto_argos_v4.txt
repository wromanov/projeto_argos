[PLANEJADA] Funcional 4C — Validação e Padronização de Dados Técnicos

Objetivo:
Aumentar a qualidade e consistência dos dados técnicos do inventário sem
retirar a flexibilidade operacional do usuário.

Princípio central:
- Padronizar o que já é conhecido.
- Permitir valores personalizados quando necessário.
- Normalizar no back-end antes de salvar.
- Não depender apenas de transformação visual por CSS.


4C.1 — Normalização cadastral

Regra oficial:
Dados cadastrais estruturados devem ser salvos e exibidos em CAIXA ALTA.

Exemplos:
- axis -> AXIS
- Axis -> AXIS
- p3265-lve -> P3265-LVE
- est-tps2-cm78 -> EST-TPS2-CM78
- stvv -> STVV
- Bolsão de Taxi -> BOLSÃO DE TAXI
- nova farm -> NOVA FARM
- h.264 -> H.264
- 00:1a:2b:3c:4d:5e -> 00:1A:2B:3C:4D:5E

Campos estruturados candidatos à normalização:
- Patrimônio.
- Nome da câmera.
- Fabricante.
- Modelo.
- Número de série.
- MAC.
- Terminal.
- Pavimento.
- Setor.
- Ambiente.
- Ponto de referência.
- Farm.
- Codec.
- Valores personalizados de Farm e Codec.

Exceções:
- Descrição detalhada.
- Observações.

Esses campos narrativos devem preservar caixa e legibilidade do texto original.

Fluxo conceitual:
- strip de espaços.
- uppercase para dado estruturado.
- validação.
- gravação.

Não espalhar .upper() pelo código.
Centralizar normalização em função/serviço reutilizável.


4C.2 — Validação sintática de IPv4 e MAC

IPv4:
- Validar que o valor informado corresponde a IPv4 sintaticamente válido.
- Não validar conectividade.
- Não validar se o endereço está ocupado.
- Não validar topologia, rede ou gateway nessa regra.

Exemplos válidos:
- 10.20.78.15
- 192.168.0.1

Exemplos inválidos:
- 10.20.300.1
- 10.20.78
- abc.def.ghi.jkl

MAC:
- Validar estrutura sintática.
- Aceitar formatos razoáveis de entrada quando possível.
- Normalizar para formato canônico:
  XX:XX:XX:XX:XX:XX
- Salvar em caixa alta.

Exemplos de entrada:
- 00:1A:2B:3C:4D:5E
- 00-1A-2B-3C-4D-5E
- 001A2B3C4D5E

Valor canônico:
- 00:1A:2B:3C:4D:5E

Observação:
Validação sintática não afirma que o MAC pertence fisicamente a um equipamento
existente e não deve rejeitar endereços localmente administrados apenas por
não corresponderem a fabricante conhecido.


4C.3 — Catálogo de Farms

Valores oficiais iniciais:
- ESTACIONAMENTO
- STVV
- ALFANDEGAMENTO
- BOLSÃO DE TAXI
- TDNA
- COANA
- FACE X
- POC
- PERSONALIZADO

UX:
- Combobox/select de valores oficiais.
- Ao selecionar PERSONALIZADO, exibir campo de texto livre.
- O banco deve armazenar o valor efetivo, não a palavra PERSONALIZADO.

Exemplo:
- seleção STVV -> camera.farm = "STVV"
- PERSONALIZADO + "Nova Farm" -> camera.farm = "NOVA FARM"

Compatibilidade:
- Câmeras existentes com valor fora do catálogo não podem deixar de ser editáveis.


4C.4 — Catálogo de Codecs

Valores oficiais iniciais:
- H.263
- H.264
- H.265
- H.265+
- PERSONALIZADO

UX:
- Combobox/select.
- PERSONALIZADO libera entrada livre.
- Normalização para caixa alta.
- O banco recebe o valor efetivo.

Objetivo adicional:
Evitar variantes equivalentes como:
- h264
- H264
- h.264
- H.264

O valor oficial deverá convergir para a representação padronizada definida.


4C.5 — Retenção

Valores rápidos:
- 15 dias
- 30 dias
- 90 dias
- 180 dias
- 360 dias
- 540 dias
- PERSONALIZADO

UX:
- Combobox/select.
- PERSONALIZADO libera entrada numérica.

Armazenamento:
- retencao_esperada_dias permanece numérico.
- A opção PERSONALIZADO nunca é armazenada como valor.

Regra mínima:
- Somente inteiro positivo.
- Não definir teto arbitrário antes de análise do domínio.


4C.6 — Compatibilidade, legado e testes

Antes de normalizar dados existentes:
- Levantar valores reais presentes no banco.
- Identificar farms e codecs não catalogados.
- Não destruir valores legítimos.
- Definir estratégia de migração segura.

Testes obrigatórios:
- IPv4 válido.
- IPv4 inválido.
- MAC com dois-pontos.
- MAC com hífen.
- MAC sem separador.
- MAC incompleto.
- MAC com caractere inválido.
- Normalização de MAC.
- Farm oficial.
- Farm personalizada.
- Codec oficial.
- Codec personalizado.
- Retenção oficial.
- Retenção personalizada.
- Retenção textual inválida.
- Retenção negativa inválida.
- Normalização para caixa alta.
- Preservação de descrição detalhada e observações.
- Compatibilidade de registros legados.

Arquitetura esperada:
- Preferir centralização de validações/normalizações.
- Avaliar cameras/validators.py.
- Não esconder regexes e regras espalhadas em templates.
- JavaScript pequeno e específico pode ser usado apenas para UX de PERSONALIZADO.
- Validação real permanece no back-end.
